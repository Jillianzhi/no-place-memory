## 1. 一句话说明项目现状

这是一个固定视角、手机竖屏优先的 Three.js 互动空间游戏。四个场景的核心状态机、Pointer Events、Raycaster、拖拽、擦拭、长按、观察、档案系统和无模型 fallback 均已建立；目前视觉重构主要完成了场景一，场景二已完成建筑空间和玩法重排，但巴士朝向与开关门资产仍未完成，场景三、四已有可玩版本但还需要按场景一、二的新质量标准继续深化。

## 2. 本项目的产品底线

以下不是建议，而是继续开发时必须保持的规则：

1. 游戏是固定视角互动空间，不是角色移动游戏。
2. 不加入 WASD、第一人称自由视角、虚拟摇杆、战斗、血条、背包或技能栏。
3. 玩家只通过点击、拖拽、滑动/擦拭、长按和观察完成流程。
4. 手机竖屏是首要画面，不得先做横屏再压缩到竖屏。
5. 物件使用真实空间比例；小物通过合理前景位置保证可操作，不靠夸张放大或巨大透明热区。
6. 视觉是中式梦核：旧中国日常空间、蓝紫冷光、潮湿反光、竹影、柔雾、花瓣和不真实的安静感。
7. 禁止赛博霓虹、仙侠、宫廷金红、恐怖血腥、跳吓、纯黑红、灰白测试模型感。
8. 用户后续不再提供正式 3D 模型，因此程序化几何体 + 独立 PNG 贴层是当前主路线。
9. `GLTFLoader` 和既有模型替换接口保留，但绝不能让项目依赖模型存在才能运行。
10. 场景美术重做时不得改变已经确认的玩法顺序。

## 3. 已完成的公共系统

### 3.1 运行与渲染

- Vite + TypeScript + Three.js 已建立并可正常构建。
- `AssetLoader` 使用 `GLTFLoader` 检查四个约定模型路径；模型不存在时自动进入程序化 fallback，不白屏。
- `Game` 负责 WebGLRenderer、场景切换、HUD、提示、档案结果和渲染循环。
- `CameraRig` 提供固定相机、轻微视差、竖横屏分别构图和对比模式固定摄影机。
- 渲染使用 ACES Filmic tone mapping、sRGB 和阴影。

### 3.2 输入与交互

- `InputSystem` 统一使用 Pointer Events，桌面鼠标和移动端触控共用一套逻辑。
- 长按阈值为 700 ms，拖拽阈值为 8 px。
- `InteractionSystem` 使用 Three.js Raycaster 命中真实 3D hotspot。
- 已支持 tap、drag、swipe、longPress、observe。
- Pointer Capture 已启用，拖拽离开原始物件后仍能继续跟随。
- 车票拖拽使用相机射线与固定 Z 平面求世界坐标，不再只按鼠标 delta 硬算。
- 车票投递使用屏幕空间重叠检测，要求指针进入检票槽且车票与槽位有足够重叠。
- 可交互热点会和可见物体同步位置，场景编辑后也会重新同步。
- 已完成的单次物件会禁用 hotspot，避免重复点击继续触发；可重复擦拭的玻璃除外。

### 3.3 档案、调试与编辑器

- `ArchiveSystem` 记录最先触碰、场景停留时间、错误次数、重复触碰、隐藏内容、拖拽成功率和观察准确率。
- 游戏结束可生成四种“非场所档案”结果。
- `?debug=1` 显示场景、FPS、flags、interactables、当前命中、模型/fallback 状态和 archiveData。
- `?compare=1` 为场景一开启参考图 50% 覆盖；`?compare=clean` 只输出干净场景。
- `?scene=1&edit=1` 打开场景布局编辑器，可移动、旋转、缩放、复原、导入和导出布局。
- 编辑器已经改成竖屏游戏画面在左、编辑面板在右，不再覆盖画面。
- 编辑结果保存在 `localStorage`，场景一、二使用 revision 号清理旧布局缓存。

## 6. 已踩过且绝对不能再犯的坑

### 6.1 不要把参考图理解成“风格参考”

用户要求的是摄影机匹配和空间重建。先匹配相机、消失点、建筑轮廓、前中后景位置，再做材质和灯光。不能根据参考图重新设计另一个“差不多风格”的房间。

### 6.2 不要再做封闭空盒子

场景一曾被做成正面后墙 + 左右墙 + 地面的方盒子，完全失去走廊纵深。场景二也不能把巴士塞在室内盒子里。空间必须符合真实建筑逻辑：开口通向室外、墙和顶有终止位置、门嵌在墙内、走道有连续动线。

### 6.3 不要用一张完整背景图冒充 Three.js 空间

完整概念图只能用来匹配构图。建筑面、远景、家具和交互层必须拆开，否则无法正确遮挡、交互、调比例或后续替换。

### 6.4 不要在美术重排时擅自改玩法

每次只改变明确要求的场景视觉或交互。场景三不能出现乐园；场景四不能加入无法归位碎片；场景二雨窗任务已经移除；场景一仍要保持广播、窗扇、雾玻璃、时钟和门的顺序。

### 6.5 热区必须对应画面中的真实对象

门的点击位置、雾玻璃擦拭范围和可见图形曾经错位。所有 hotspot 必须在最终布局后从视觉对象 Box3 同步或建立精确代理。不能为了好点而把透明热区扩到画面任意位置。

### 6.6 不要用独立门片硬贴在整车上

不同批次生成的整车与车门透视不可能自然吻合。巴士必须使用同一整车资产的关门/开门成对状态，切换整张整车 PNG，车门 hotspot 单独保留。

### 6.7 不要让拖拽物脱离指针

拖拽物需要 Pointer Capture、拖拽平面和按下时的世界偏移。不能只累加屏幕 delta，也不能鼠标离开物件后停止更新。车票允许分段拖动，未投递成功时不能弹回不可见旧坐标。

### 6.8 不要让已完成物件继续响应

广播、时钟、电子屏等单次任务完成后必须禁用热点。状态恢复时也要根据 flags 正确禁用。玻璃擦拭是例外，可继续擦到完全干净。

### 6.9 不要让 `localStorage` 旧布局覆盖新代码

场景重排后必须提升 `SceneLayoutStore` 对应 revision，否则旧编辑器坐标会继续覆盖新布局，导致“代码明明改了但浏览器没变化”。场景一当前 revision 为 `corridor-3d-v15`，场景二为 `waiting-hall-3d-v13`。

### 6.10 不要先做横屏再缩到竖屏

竖屏要独立设置相机、布局、拖拽边界和 UI。需要在 375 × 812、390 × 844、430 × 932 三个尺寸检查裁切、层级、物件大小和点击面积。

### 6.11 不要把编辑面板盖在手机预览上

编辑模式应保持 9:16 画面和侧栏并排。正常游戏 UI 也不能遮挡关键交互物件。

### 6.12 不要把“白膜”当成完成

程序化几何体必须有合适的旧材质、贴图、粗糙度、色差、潮湿反光和遮挡关系。纯色干净平面只可用于短期结构校准，不能进入交付画面。

### 6.13 不要堆满屏特效掩盖布局问题

雾、粒子和花瓣只能在建筑、比例和动线正确后增加。特效应有前中后层级，但不能遮住门、车票、检票槽等核心对象，也不能让移动端掉帧。

### 6.14 不要声称“已经替换”但没有逐文件核对

素材有多个更新版本，必须检查实际代码引用路径、透明区域、裁切参数和浏览器截图。用户提供更新包后，旧版本不能继续被引用而不说明。

### 6.15 不要只跑 build 就认为交互通过

`npm run build` 只能证明编译成功。每个场景还必须用浏览器真实点击、长按、拖拽和擦拭完整走通。尤其要检查移动端命中范围和完成后的状态切换。

### 6.16 不要用短命令启动临时预览后就结束进程

预览服务需要保持常驻。交接时先用 `curl` 验证 4173 是否返回 200；如果没有，再用长期会话启动 preview。不要告诉用户“可以访问”而实际进程已经退出。

## 10. 已知技术债与注意事项

- 当前项目目录整体尚未形成可靠 Git 提交历史，不能只依赖 `git log` 判断修改内容；接手后应先建立基线提交或完整备份。
- `SceneEditor.getEditableObjects()` 当前存在重复 `objects.push(object)`，会让编辑器下拉列表出现重复项，后续应修复。
- `?compare=1` 目前只针对场景一参考图，不是四场景通用工具。
- 自动化测试缺失，当前主要依赖真实浏览器 QA。
- 正式音频未接入。
- 大尺寸透明 PNG 较多，需要关注显存、纹理尺寸和移动端性能。
- GLTF 模型接口保留，但当前没有正式模型；不要围绕不存在的模型重构核心玩法。
- 场景一的代码命名仍有“curtain”、场景三仍有“red_paper”，这是兼容命名，不代表产品语义。

## 11. 交接时的最终判断标准

不要用“代码写完了”判断完成。只有同时满足以下四项，某次迭代才算完成：

1. 画面空间结构符合参考图和真实建筑逻辑。
2. 物件比例、位置、遮挡和前中后景关系合理。
3. 手机竖屏上交互顺滑，热点与可见物件严格对应。
4. 浏览器完整流程实测通过并且 `npm run build` 成功。

当前最重要的接棒动作不是继续添加装饰，而是先完成场景二“车尾朝向画面”的关门/开门整车资产和精确车门热区，彻底移除独立车门叠片方案。
